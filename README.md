# Linux 프로세스 장애 분석 및 이슈 리포팅

Memory Leak/OOM, CPU 과점유, Deadlock을 재현하고 관제 데이터와 실행 로그를 근거로 원인을 분석하는 미션이다. 각 장애의 설정 변경 전후를 비교하고, 결과를 GitHub Issue 형식의 기술 리포트로 정리한다.

> **문서 상태: 실습 전 초안**
>
> 실행 파일명, 환경변수 값, PID, 측정 수치, 종료 시각, 스크린샷은 실습하며 채운다. 아래 절차와 파일 경로는 계획이며, 완료되었거나 검증된 결과를 의미하지 않는다.

## 1. 미션 목표와 제출물

### 미션 목표

- 메모리 사용량이 계속 증가하는 현상과 애플리케이션 보호 종료를 설명한다.
- 특정 프로세스의 CPU 과점유와 Watchdog 종료를 관측한다.
- PID가 유지되는 무응답 상태를 확인하고, 스레드 간 락 대기 관계를 분석한다.
- 같은 조건에서 환경변수 하나를 변경하여 Before & After를 비교한다.
- 관측 사실과 원인 추론을 구분하고, 재현 가능한 기술 리포트를 작성한다.

### 최종 제출물

| 제출물 | 포함할 내용 |
| --- | --- |
| OOM 이슈 리포트 | 메모리 상승, 종료 직전·직후 로그, `MEMORY_LIMIT` 변경 전후 비교 |
| CPU 이슈 리포트 | 프로세스별 CPU 급상승, Watchdog 종료 로그, `CPU_MAX_OCCUPY` 변경 전후 비교 |
| Deadlock 이슈 리포트 | PID 유지, 스레드 상태, 마지막 로그, `MULTI_THREAD_ENABLE` 변경 전후 비교 |
| 공통 이슈 템플릿 | 현상, 증거, 원인 분석, 조치 및 검증의 공통 구조 |

최종 결과는 GitHub Repository 링크 또는 PDF로 제출한다. 이 저장소는 리포트와 증거 자료를 함께 정리하는 용도로 사용한다.

### Git 추적 기준

- README, 관제 스크립트, 이슈 템플릿, 리포트, 제출용 증거 로그와 스크린샷을 추적한다.
- 제공 바이너리와 압축 배포본은 `data/`에 보관하고 추적에서 제외한다.
- 키 디렉터리, 키 파일, 개인용 `.env`, 가상환경, 메모리 덤프는 제외한다.
- 루트의 `logs/`는 실행 중 쌓이는 로컬 로그 보관용으로 제외한다.
- **제출할 로그는 `docs/logs/`에 보관한다. `*.log` 전체를 제외하지 않는다.**
- `.env.example`과 `.env.sample`은 예제 설정 파일로 추적할 수 있다. 실제 비밀 값은 넣지 않는다.
- `.gitignore`는 이미 Git이 추적 중인 파일에는 소급 적용되지 않는다.

## 5. 관측과 비교 원칙

### 기존 관제 스크립트 보완

이전 실습의 `monitor.sh`는 `agent-app-linux-arm64` 프로세스를 확인하며, CPU와 MEM은 시스템 전체 값으로 측정한다.

이번 실습에서는 사본을 준비해 대상 앱 이름을 맞추고 프로세스별 CPU와 메모리 관측 항목을 추가한다. 시스템 전체 값과 프로세스별 값을 구분하여 기록한다.

| 관측 항목 | 기록할 내용 | 해석 시 확인 사항 |
| --- | --- | --- |
| 시각 | 시간대가 포함된 측정 시각 | 앱 로그와 관제 로그의 시간 기준 통일 |
| PID / PPID | 앱과 부모·자식 프로세스 관계 | 여러 PID가 있으면 실제 측정 대상을 명시 |
| 프로세스 CPU | 대상 PID의 CPU 사용률 | 시스템 전체 CPU와 계산 기준 구분 |
| 프로세스 메모리 | RSS, 필요하면 %MEM | RSS의 단위와 대상 PID 명시 |
| 스레드 상태 | TID, 상태, CPU 시간, 대기 지점 | 여러 시점의 출력을 비교 |
| 실행 로그 | 부팅, 진행, 경고, 보호 종료, 마지막 로그 | 로그 원문과 발췌 구간 보관 |
| 종료 정보 | 종료 시각, 종료 코드, 종료 메시지 | 앱 보호 종료와 수동 종료 구분 |
| 관측 기간 | 시작부터 종료 또는 관측 종료까지의 시간 | 관측 종료 시 생존한 경우 그 사실을 명시 |

RSS는 프로세스의 메모리 중 RAM에 상주하는 부분의 크기다. 메모리 증가 패턴을 볼 때 시스템 전체 MEM 비율과 함께 확인한다. 여러 프로세스의 RSS를 합치면 공유 메모리가 중복 계산될 수 있으므로 PID별 값과 집계 방식을 남긴다.

`ps`의 %CPU는 일반적으로 프로세스 생존 기간의 평균이고, `top`은 갱신 구간의 사용량을 관측한다. 급상승 구간은 `top` 또는 구간별 관제 측정을 함께 사용해 확인한다.

### 실험 운영 원칙

1. 매 실행에 `oom-before`, `oom-after`처럼 구분 가능한 이름을 붙인다.
2. 시작 시각, 전체 실험 설정, 측정 PID와 수집 간격을 기록한다.
3. Before & After에서는 목표 환경변수 하나만 바꾸고 다른 조건을 유지한다.
4. 실행 로그와 관제 로그를 실험별로 분리해 이전 결과를 덮어쓰지 않는다.
5. 갑작스러운 장애를 놓치지 않도록 초기에는 초 단위로 관측하고, 실제 발생 속도에 맞춰 간격을 조정한다.
6. 다른 장애가 먼저 발생하면 그 사실을 기록하고, 목표 장애를 관측할 수 있도록 조건을 다시 정한다.
7. 재시작이나 수동 종료가 필요하면 먼저 증거를 확보하고 조작 시각을 남긴다.
8. 장애가 발생하지 않은 실행은 “관측 기간 동안 미발생”으로 기록하고 관측 시간을 명시한다.

## 6. 실습 진행 절차

### 6.1 환경 및 실행 파일 확인

Mac 터미널에서 기존 컨테이너 상태를 확인한다.

~~~bash
docker ps -a --filter name=agent-lab
~~~

실행 중이면 접속한다. 정지 상태라면 먼저 컨테이너를 시작한다.

~~~bash
docker exec -it agent-lab bash
~~~

컨테이너 내부에서 아래 항목을 확인한다. 환경 점검은 관리자 셸에서 할 수 있으나 실제 앱 실행은 일반 사용자로 수행한다.

~~~bash
whoami
uname -sm
date '+%Y-%m-%d %H:%M:%S %Z'
id agent-admin
ls -l /mission-data
ls -l /home/agent-admin/agent-app
ps -ef | grep -E '[a]gent-(app|leak)'
ss -ltnp 'sport = :15034'
~~~

확인할 내용:

- 제공 실행 파일과 리눅스 아키텍처가 맞는가?
- `agent-admin` 계정이 존재하는가?
- 이번 미션용 바이너리는 어디에 있는가?
- 기존 앱이 실행 중이거나 `15034` 포트를 사용 중인가?
- 로그를 비교할 시간대가 맞는가?

### 6.2 실행 환경과 로그 수집 준비

- 필수 디렉터리와 권한, 테스트 키 파일을 확인한다.
- 세 가지 실험 변수의 초기값을 정하고 기록한다.
- 일반 사용자에게 환경변수가 전달되는지 확인한다.
- 부팅 성공 및 `15034` 포트 리슨을 확인한다.
- 관제 스크립트 사본의 대상 프로세스와 측정 항목을 확인한다.
- 실험별 실행 로그와 관제 로그가 각각 저장되는지 확인한다.

정확한 실행 파일명, 실행 명령, 환경변수 설정 경로는 환경 확인 후 이 절에 반영한다.

### 6.3 OOM / MemoryGuard 분석

**알아둘 개념**

메모리는 프로그램이 작업 중인 데이터를 올려 두는 공간이다. 사용이 끝난 데이터를 계속 붙잡고 있으면 점유량이 커질 수 있다. 다만 RSS 증가만으로 누수를 확정할 수는 없으므로, 시간별 수치와 실행 로그를 함께 해석한다.

이 미션에서는 로그를 통해 앱 내부 MemoryGuard가 메모리 기준을 넘겨 종료했는지 확인한다. 애플리케이션의 자체 보호 종료와 리눅스 커널 OOM Killer에 의한 종료는 구분하여 서술한다.

**실습 순서**

1. 초기 `MEMORY_LIMIT`과 나머지 설정을 기록하고 앱을 실행한다.
2. `monitor.sh`와 프로세스별 RSS로 시간에 따른 메모리 증가를 수집한다.
3. 종료 직전·직후 로그에서 메모리 초과와 자체 종료 메시지를 찾는다.
4. 로그가 명시하는 종료 원인과 종료 코드를 기록한다.
5. 허용 범위 안에서 `MEMORY_LIMIT`을 높여 재실행한다.
6. 메모리 추이, 종료 여부, 생존 시간을 비교한다.

| 비교 항목 | Before | After |
| --- | --- | --- |
| MEMORY_LIMIT (MB) | 실습 후 입력 | 실습 후 입력 |
| 고정한 CPU_MAX_OCCUPY | 실습 후 입력 | 동일 값 |
| 고정한 MULTI_THREAD_ENABLE | 실습 후 입력 | 동일 값 |
| 초기 / 마지막 측정 RSS | 실습 후 입력 | 실습 후 입력 |
| 생존 시간 / 관측 시간 | 실습 후 입력 | 실습 후 입력 |
| 종료 여부 및 핵심 로그 | 실습 후 입력 | 실습 후 입력 |

**설명할 핵심:** “메모리 사용량 증가와 보호 종료 로그를 함께 확인했습니다. 임계값을 올린 뒤 생존 시간이 어떻게 바뀌었는지 비교했습니다.”

임계값 상향은 메모리 증가의 원인을 제거하지 않는다. 관측 결과를 바탕으로 임시 조치의 효과와 한계를 구분한다.

### 6.4 CPU 과점유 / Watchdog 분석

**알아둘 개념**

CPU는 프로그램의 계산을 처리한다. 특정 프로세스가 실행 시간을 많이 사용하면 같은 CPU 자원을 필요로 하는 다른 작업의 대기 시간이 늘어날 수 있다. 실제 지연 정도는 사용 가능한 코어 수와 작업 조건에 따라 달라진다.

Watchdog는 상태를 감시하다 조건에 따라 보호 조치를 수행하는 장치다. 이번 앱에서 `CPU_MAX_OCCUPY`가 어떻게 적용되는지는 실행 로그와 변경 전후 관측으로 확인한다. 이 변수를 설정했다고 운영체제가 CPU 사용량을 강제로 제한한다고 단정하지 않는다.

**실습 순서**

1. 초기 `CPU_MAX_OCCUPY`와 나머지 설정을 기록하고 실행한다.
2. `top`, `ps`, 관제 데이터를 통해 해당 프로세스의 CPU 급상승을 확인한다.
3. 종료 로그에서 Watchdog의 판단과 종료 조치를 확인한다.
4. 허용 범위 안에서 `CPU_MAX_OCCUPY`를 변경하여 재실행한다.
5. CPU 사용 양상, 종료 여부, 생존 시간을 비교한다.

| 비교 항목 | Before | After |
| --- | --- | --- |
| CPU_MAX_OCCUPY (%) | 실습 후 입력 | 실습 후 입력 |
| 고정한 MEMORY_LIMIT | 실습 후 입력 | 동일 값 |
| 고정한 MULTI_THREAD_ENABLE | 실습 후 입력 | 동일 값 |
| 관측된 프로세스 CPU | 실습 후 입력 | 실습 후 입력 |
| 생존 시간 / 관측 시간 | 실습 후 입력 | 실습 후 입력 |
| Watchdog 로그 및 종료 여부 | 실습 후 입력 | 실습 후 입력 |

**설명할 핵심:** “시스템 전체 값뿐 아니라 대상 프로세스의 CPU 급상승을 확인하고, 종료가 Watchdog 보호 조치였는지 로그로 판단했습니다.”

### 6.5 Deadlock 분석

**알아둘 개념**

스레드는 한 프로세스 안에서 작업을 수행하는 실행 흐름이다. 락은 여러 스레드가 공유 자원을 동시에 변경하지 못하도록 접근을 제한한다.

예를 들어 A가 락 1을 가진 채 락 2를 기다리고, B가 락 2를 가진 채 락 1을 기다리면 서로 진행할 수 없다. 실제 앱에 이러한 순환 대기가 존재하는지는 마지막 로그와 스레드 상태로 추론한다.

| 교착상태 조건 | 뜻 |
| --- | --- |
| 상호 배제 | 자원을 한 번에 하나의 스레드만 사용 |
| 점유 대기 | 자원을 보유한 상태에서 다른 자원을 기다림 |
| 비선점 | 보유 중인 자원을 강제로 회수하지 못함 |
| 순환 대기 | 자원을 기다리는 관계가 고리를 이룸 |

**실습 순서**

1. `MULTI_THREAD_ENABLE=true`로 실행하고 진행 로그를 수집한다.
2. 진행이 멈추면 PID와 프로세스 상태를 확인한다.
3. `top -H` 또는 `ps -L`을 여러 시점에 수집해 스레드 상태와 CPU 시간 변화를 비교한다.
4. 같은 기간의 메모리 사용량과 로그 증가 여부를 확인한다.
5. 마지막 로그에서 어떤 스레드가 어떤 자원을 보유·대기하는지 정리한다.
6. 증거를 확보한 뒤 종료하고, `MULTI_THREAD_ENABLE=false`로 재실행한다.
7. 나머지 조건과 관측 기간을 맞춰 진행 로그 및 교착 재현 여부를 비교한다.

PID 존재, 낮은 CPU, 고정된 메모리만으로 교착상태를 확정하지 않는다. 정상 대기나 좀비 상태 등과 구분하고, 로그에 나타난 스레드별 락 보유·대기 관계를 함께 제시한다.

| 비교 항목 | Before | After |
| --- | --- | --- |
| MULTI_THREAD_ENABLE | true | false |
| 고정한 MEMORY_LIMIT | 실습 후 입력 | 동일 값 |
| 고정한 CPU_MAX_OCCUPY | 실습 후 입력 | 동일 값 |
| PID 및 프로세스 상태 | 실습 후 입력 | 실습 후 입력 |
| 스레드 상태·CPU 시간 변화 | 실습 후 입력 | 실습 후 입력 |
| 관측 기간의 메모리 변화 | 실습 후 입력 | 실습 후 입력 |
| 마지막 로그 및 로그 증가 여부 | 실습 후 입력 | 실습 후 입력 |
| 교착 재현 여부 / 관측 기간 | 실습 후 입력 | 실습 후 입력 |

**설명할 핵심:** “프로세스가 살아 있어도 작업은 멈출 수 있습니다. 스레드 상태와 마지막 로그에서 서로의 자원을 기다리는 관계를 찾고, 멀티스레드 설정 변경 후 진행 여부를 비교했습니다.”
